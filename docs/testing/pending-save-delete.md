# 同じ画面の遅延保存による削除メモの復活を防ぐ

## 再現

1. メモの位置を変更し、500msのdebounce保存を予約する。
2. 保存タイマーが走る前に、そのメモを削除する。
3. 削除直後は保存一覧から消えるが、タイマーが走ると古いメモが新規として書き戻される。

既にバッチ読込が始まっている場合や、即時保存の読込が遅れて返る場合も、削除後の古い書込で復活しました。未保存Mapから対象IDを除くだけでは、開始済みの書込を止められません。

## 修正範囲

- 同じStorageインスタンス内の即時保存・バッチ保存・削除をPromiseキューで直列化する。
- バッチは予約時点のスナップショットを維持し、後から来た新しい編集を取り込まない。
- メモごとのメモリ内世代番号を保持し、削除成功時に世代を進める。削除後に実行される古い予約バッチは無効化する。永続データに削除印を追加しない。
- 削除成功後に対象の保留書込を取り消す。最後の保留書込ならタイマーも取り消す。
- 削除失敗時は保留編集を残し、失敗した操作が後続キューを停止させない。
- 削除完了後に改めて呼び出した明示保存は許可する。恒久的な削除マークは作らない。

永続形式、拡張権限、保存先、インポート/エクスポート仕様は変更しません。

## 限界

- 同じStorageインスタンス内のsaveMemo/deleteMemoが対象です。別タブ、popup、background等の別インスタンス間の全体排他ではありません。
- importAll/importMerge/clearや直接のstorage.local書込を、このキューで排他する変更ではありません。
- バッチ書込そのものの失敗時に、再試行や永続キューを提供するものではありません。
- 実ChromeでのE2Eは未検証です。
- main基準では、既存のchrome型不足に由来する24診断が残ります（この修正でエラー種類・件数は増えていません）。型の復旧は独立したPR #3の範囲です。

PRはdraftを維持し、mainへのmerge・リリース・本番配備は行いません。
